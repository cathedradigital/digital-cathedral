# Cathedra Digital — Security Audit

**Audit date:** 2026-09-15  
**Audit branch:** `security/cathedra-audit-20260915`  
**Baseline:** `main`

## Scope

Initial repository-level audit covering authentication/authorization, Supabase Edge Functions, RLS/security migrations, CI quality gates, secrets handling, and the existing production-hardening work.

## Initial findings

### High — service-role authentication path requires strict isolation

The existing shared Edge Function guard accepts `Authorization: Bearer <SUPABASE_SERVICE_ROLE_KEY>` as an administrative path. This is only safe when the service-role key can never be supplied by an untrusted caller or exposed to a client. The audit therefore treats every caller of `assertCronOrAdmin` as requiring an explicit review of its invocation path and deployment configuration.

### High — production-hardening branch is not part of `main`

The branch `security/production-hardening-20260910` is 55 commits ahead of `main` and contains the current security hardening migration, shared Edge Function guards, rate limiting, validation helpers, security tests, and a large test suite. These changes are not automatically effective in production merely because they exist on that branch.

### Medium — CI currently validates typecheck/lint/build, but not the repository test suite

`main` exposes `typecheck`, `lint`, and `build` scripts and the GitHub Actions workflow runs those checks. The package manifest does not currently expose a test script, so the substantial tests present on the hardening branch are not represented by a standard `npm test` CI gate on `main`.

### Medium — RLS hardening exists but must be validated against the actual schema

The hardening migration centralizes role checks and restricts `user_sensitive_data` and `telemetry_settings`. The next audit phase must verify table existence, grants, policies, SECURITY DEFINER ownership/search_path behavior, and negative tests for cross-user access.

## Next audit phases

1. Inventory all Edge Functions and classify public, authenticated, admin, cron, webhook, and service-role paths.
2. Trace all uses of `SUPABASE_SERVICE_ROLE_KEY` and `CRON_SECRET`.
3. Review every RLS policy for sensitive tables and add/verify negative tests.
4. Review webhook signature/idempotency handling, especially payment flows.
5. Review client/server Supabase boundaries and browser bundle exposure.
6. Establish a reproducible test command and CI security gate.
7. Compare the hardening branch against `main` and selectively promote verified fixes through this audit branch.
8. Re-run build/typecheck/lint/tests before opening a PR.

## Audit rule

A finding is considered fixed only after the code change and a corresponding validation path have both been verified.
